## 1. 总则与文档架构

### 1.1 双轴模型说明

本手册采用 **"横向流程轴 × 纵向技术轴"** 双轴结构，确保任何发布项都能被精确定位和审计：

> **MAS-TS 适用性**: 本手册完整覆盖 L0~L2 层（基础设施/后端/全栈链路）。L3(前端应用层)/L4(用户界面层)/桌面端 对 MAS-TS（纯后端 CLI 评测框架）不适用。

```
                    技术纵深轴 (Technical Stack)
    L4 用户界面层  │ 交互 │ 无障碍 │ 国际化 │ AI流式渲染 │
    L3 前端应用层  │ Web │ 桌面壳 │ 移动端 │ 性能预算   │
    L2 全栈链路层  │ API契约 │ Trace贯通 │ 错误码映射 │ 认证同步 │
    L1 后端服务层  │ API │ BFF │ 微服务 │ AI推理 │ 数据库  │
    L0 基础设施层  │ 容器 │ 网络 │ 存储 │ K8s │ CDN    │
                   └────────────────────────────────────────┘
    Gate 0 需求冻结    Gate 1 开发完成    Gate 2 内测通过    Gate 3 预发验收    Gate 4 生产发布
         │                │                │                │                │
      PRD签审          Code Review        Alpha测试        Beta测试         灰度发布
      设计评审         单元测试           功能验收         性能压测         全量发布
      架构评审         安全扫描           兼容性测试       渗透测试         监控就绪
      可行性评估       构建产物签名       UAT签字          混沌测试         回滚验证
```

### 1.2 成熟度分级

| 等级 | 后端要求（MAS-TS 核心） | 全栈链路 | Agent/AI 要求 | 阻塞项 |
|------|------------------------|---------|-------------|--------|
| **Experimental** | 日志+回滚+安全基线+可观测性 | API契约存在，核心链路可观测 | 高危操作有确认，沙箱隔离 | 可降级运行 |
| **Beta** | 全量审计，允许2个例外 | Trace贯通，错误码覆盖80% | 幻觉率≤5%，Prompt注入防护 | 需审批 |
| **GA** | 零例外，混沌测试通过，SLO定义 | 契约自动生成，Mock与生产一致，全链路SLO | 多模型辩论通过，级联策略测试通过 | **全票通过** |

### 1.3 五大验收维度权重

| 维度 | 代号 | 权重 | 负责团队 | 自动化程度 |
|------|------|------|---------|-----------|
| 功能完整性 | FUNC | 25% | Product + QA | 70% |
| 工程质量 | ENGR | 25% | Engineering | 90% |
| 安全合规 | SEC | 20% | Security + Legal | 85% |
| 性能体验 | PERF | 15% | SRE + QA | 80% |
| 运维就绪 | OPS | 15% | SRE + DevOps | 75% |

## 2. 流程框架层：Gate 评审模型

### 2.1 评审类型总览

| 类别 | 项目数 | 阻塞上线 | 可例外 | 对应Gate |
|------|--------|---------|--------|---------|
| 生产就绪与发布决策 | 5项 | 全部 | 0 | Gate 0~4 |
| 安全与合规 | 7项 | 5项 | 2项 | Gate 1~3 |
| 质量与测试 | 10项 | 6项 | 4项 | Gate 1~2 |
| 可观测性与可靠性 | 5项 | 4项 | 1项 | Gate 3 |
| 数据与容量 | 4项 | 3项 | 1项 | Gate 1~3 |

### 2.2 Gate 0 — 需求冻结

**触发时机**: PRD定稿，进入开发前
**参与方**: 产品、架构、开发、测试、数据、设计
**输出物**: 需求评审纪要、技术设计文档、可行性报告

| 评审项 | 英文名称 | 阻塞 | 通过标准 |
|--------|---------|------|---------|
| 需求评审 | PRD/BRD Review | ✅ | 需求无歧义，验收标准可量化 |
| 技术设计评审 | Technical Design Review | ✅ | 架构无单点故障，依赖分级清晰 |
| 数据库变更评审 | Schema Change Review | ✅ | DDL向后兼容，大表有分片策略 |
| 可行性评估 | Feasibility Assessment | ✅ | 技术风险可控，资源已排期 |

### 2.3 Gate 1 — 开发完成

**触发时机**: 代码合并前，功能开发完成
**参与方**: 开发、架构、安全、平台工程
**输出物**: PR合并记录、扫描报告、构建产物

| 评审项 | 英文名称 | 阻塞 | 通过标准 |
|--------|---------|------|---------|
| 代码评审 | Code Review | ✅ | 必审8项全部通过 |
| 静态安全测试 | SAST | ✅ | 0 Critical, 0 High |
| 依赖漏洞审计 | Dependency Vulnerability Audit | ✅ | 0 Critical/High CVE |
| CI/CD流水线审计 | CI/CD Pipeline Audit | ✅ | 构建环境隔离，产物签名验证 |
| 测试就绪评审 | Test Readiness Review (TRR) | ⚠️ | 测试环境、用例、数据就位 |
| 测试用例评审 | Test Case Review | ⚠️ | 三方评审覆盖度达标 |

**Code Review 必审8项**:
```
□ 架构设计符合既定方案
□ 敏感操作有审计日志
□ 并发场景有锁/事务保护
□ 输入参数有校验和消毒
□ 错误处理不吞异常
□ 无硬编码密钥/配置
□ API 变更有版本控制
□ 数据库变更有回滚脚本
```

### 2.4 Gate 2 — 内测通过 (Alpha)

**触发时机**: 功能开发完成，进入测试阶段
**参与方**: 测试、开发、产品、业务、UX
**输出物**: 测试报告、UAT签字、兼容性报告

| 评审项 | 英文名称 | 阻塞 | 通过标准 |
|--------|---------|------|---------|
| 系统集成测试 | System Integration Testing (SIT) | ✅ | 多系统接口与数据流验证通过 |
| 用户验收测试 | User Acceptance Testing (UAT) | ✅ | 业务方签字，核心场景全覆盖 |
| 回归测试 | Regression Testing | ✅ | 新改动未破坏已有功能 |
| 端到端测试 | End-to-End (E2E) Testing | ⚠️ | 真实用户操作流程模拟通过 |
| 无障碍审查 | Accessibility Review (a11y) | ⚠️ | 键盘导航、ARIA、色盲友好 |
| 体验审查/设计走查 | UX Review / Design QA | ⚠️ | 交互、视觉、动效符合设计稿 |

**Alpha 通过标准**:
- P0 缺陷 = 0
- P1 缺陷 ≤ 3（有规避方案）
- 用户满意度 ≥ 4.0/5.0

## 3. 技术实施层：全栈分层审计

### 3.1 分层定义

| 层级 | 定义 | 审计焦点 |
|---|---|---|
| **L0 基础设施层** | 容器、网络、存储、K8s、CDN | 资源隔离、网络策略、存储可靠性 |
| **L1 后端服务层** | API、BFF、微服务、AI推理服务、数据库 | API契约、性能基线、安全头、可观测性 |
| **L2 全栈链路层** | API契约、类型共享、端到端数据流、会话一致性 | **跨端一致性审计（核心）** |
| **L3 前端应用层** | Web/React/Vue、桌面壳（Tauri）、移动端WebView | Core Web Vitals、包体积、错误边界 |
| **L4 用户界面层** | 交互体验、无障碍、国际化、AI流式输出渲染 | 体验走查、a11y、暗黑模式 |

> **审计原则**：后端决定"系统是否稳定"，前端决定"用户是否可用"，全栈链路决定"数据是否一致"。三层全部通过方可上线。

### 3.2 L1 后端服务层审计

| 维度 | 关键检查项 | 全栈联动点 |
|---|---|---|
| **API契约** | OpenAPI/Proto 定义完整，版本化策略明确 | 前端类型生成源头 |
| **错误码规范** | 统一错误码体系，业务错误与系统错误分离 | 前端错误处理映射 |
| **CORS/安全头** | 允许域名白名单，CSP 策略与前端对齐 | 前端部署域名必须预登记 |
| **性能基线** | P99 延迟 < 目标值，支持 Brotli/Gzip | 前端 TTFB 依赖项 |
| **可观测性** | 每个接口有 RED 指标（Rate/Errors/Duration） | 前端可关联 trace_id |
| **限流熔断** | 按用户/按IP限流，429 响应规范 | 前端需实现退避重试 |
| **部署与回滚** | 蓝绿/金丝雀发布，数据库变更向后兼容 | 前端静态资源缓存策略联动 |

### 3.3 L3 前端应用层审计

#### 3.3.1 性能基线（Core Web Vitals & Beyond）

| 检查项 | 通过标准（Web） | 通过标准（桌面端 Tauri） | 严重等级 |
|---|---|---|---|
| **LCP（最大内容绘制）** | ≤ 2.5s（3G 模拟） | 首屏白屏时间 ≤ 1.5s | P0 |
| **INP（交互延迟）** | ≤ 200ms | 主线程阻塞 ≤ 50ms/任务 | P0 |
| **CLS（累积布局偏移）** | ≤ 0.1 | 窗口resize/数据加载无跳动 | P0 |
| **TTFB（首字节时间）** | ≤ 600ms | 本地资源加载 ≤ 100ms | P1 |

| **沙箱隔离** | 前端代码编辑器/预览iframe沙箱化 | 后端执行环境容器化/权限最小化 | 前后端沙箱策略文档化 | P0 |
| **Human-in-the-Loop** | 中断点 UI：策略规划层展示计划供确认，执行层展示进度可暂停 | 中断 API：支持 cancel/confirm/pause 信号 | 中断响应时间 ≤ 500ms | P0 |
| **模型版本对齐** | 前端显示当前使用模型版本，切换模型需确认 | 后端模型路由锁定，不自动漂移 | 版本切换前后端同步 | P1 |
| **多模态渲染** | 图片/视频/音频流式加载有占位图，错误降级 | 媒体转码/压缩策略，CDN 分发 | 端到端媒体加载时间 ≤ LCP 目标 | P1 |

### 5.2 最小可上线集 (MVP)

即使 Experimental 等级，以下跨端基线不可妥协：

| 层级 | 不可妥协项 |
|---|---|
| **后端** | 可回滚、日志可检索、无 Critical 漏洞、有 SLO |
| **前端** | 首屏可加载、无 XSS 漏洞、错误边界覆盖、API 错误有提示 |
| **桌面端** | Capability 非全局授权、敏感数据不存明文、可更新 |
| **全栈链路** | 认证状态同步、核心链路 Trace 可贯通、Token 过期不死循环 |
| **AI/Agent** | 高危操作有确认、沙箱隔离、HITL中断点、幻觉率≤5% |

## 6. 大厂实践映射

### 6.1 Google — SRE 发布模型
- **Error Budget**: 每月可用错误预算耗尽则停止发布
- **SLI/SLO**: 每个服务定义明确的 SLI，发布不得降低 SLO
- **Canary Analysis**: 基于统计学的灰度分析，自动判定通过/回滚
- **PRR**: 新服务首次上线 / 架构重大变更 / 成熟度等级跃迁时强制

### 6.2 Meta — Production Engineering Review
- **PE团队主导**: 区别于SRE，更强调工程化改造
- **成熟度分级**: Experimental → Beta → GA 逐级提升门禁
- **混沌工程**: 季度故障演练纳入PRR

### 6.3 Microsoft — Go-Live Checklist
- **UAT强制**: 产品级发布前必须业务方签字
- **数据迁移**: 所有数据迁移必须有校验和回滚方案
- **支持就绪**: 客服/运营物料必须齐备

### 6.4 GitLab — Production Readiness Assessment
- **成熟度驱动**: 按Experimental/Beta/GA定义不同检查项
- **异步评审**: 支持Issue驱动，60分钟同步会审
- **持续跟踪**: 例外项到期自动提醒

### 6.5 Netflix — Chaos Engineering 前置
- **Chaos Monkey**: 预发环境随机终止实例，验证弹性
- **Canary Release**: 基于用户画像的精细灰度
- **Automated Rollback**: 指标异常自动回滚，无需人工审批

### 6.6 字节跳动 — AB 实验驱动
- **实验覆盖**: 新功能100%走 AB 实验
- **指标门禁**: 核心指标不下跌方可全量
- **发布平台**: 一站式发布平台集成所有门禁检查

### 6.7 阿里 — 安全生产三板斧
- **可监控**: 发布必须有监控看板
- **可灰度**: 必须支持流量灰度
- **可回滚**: 必须支持一键回滚
- **全链路压测**: 双11/春节标配，影子库压测

### 6.8 腾讯 — 四级签字流程
- **测试→项目→产品→运维**: 四级签字方可上线
- **上线审批**: 内部OA流程强卡控
- **灰度评审**: 灰度维度（百分比/用户ID/地域/设备）必须确认

### 7.1 自动化验收流水线 (CI/CD)

```yaml
# .github/workflows/release-gate.yml
name: Release Gate
on:
  pull_request:
    branches: [main]

jobs:
  gate-0-requirements:
    runs-on: ubuntu-latest
    steps:
      - name: PRD Traceability Check
        run: python scripts/rtm_validator.py --prd docs/prd.md
      - name: Design Doc Link Check
        run: python scripts/design_doc_checker.py

  gate-1-code-quality:
    needs: gate-0
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Unit Tests
        run: pytest --cov=src --cov-report=xml
      - name: Coverage Gate
        run: |
          coverage=$(cat coverage.xml | grep -o 'line-rate="[0-9.]*"' | head -1)
          if (( $(echo "$coverage < 0.80" | bc -l) )); then exit 1; fi
      - name: SAST Scan
        uses: github/codeql-action/analyze@v3
      - name: Dependency Check
        run: snyk test --severity-threshold=high
      - name: Frontend Bundle Size
        run: npx bundlesize
      - name: Lighthouse CI
        run: lhci autorun

  gate-2-integration:
    needs: gate-1
    runs-on: ubuntu-latest
    steps:
      - name: Integration Tests
        run: pytest tests/integration/
      - name: E2E Tests
        run: npx playwright test
      - name: API Contract Test
        run: schemathesis run openapi.yaml
      - name: Mock Consistency Check
        run: python scripts/mock_validator.py --backend openapi.yaml --frontend src/mocks/

  gate-3-performance:
    needs: gate-2
    runs-on: ubuntu-latest
    steps:
      - name: Load Test
        run: k6 run load-test.js
      - name: Chaos Test
        run: chaos-mesh run chaos-experiment.yaml
      - name: Tauri Cargo Audit
        run: cargo audit
      - name: Desktop Binary Sign Check
        run: python scripts/sign_verifier.py

  gate-4-security:
    needs: gate-3
    runs-on: ubuntu-latest
    steps:
      - name: Container Scan
        run: trivy image myapp:${{ github.sha }}
      - name: DAST Scan
        run: zap-baseline.py -t https://staging.myapp.com
      - name: Secret Scan
        run: truffleHog --regex --entropy=False .
      - name: SBOM Generation
        run: syft myapp:${{ github.sha }} -o spdx-json > sbom.json
```
